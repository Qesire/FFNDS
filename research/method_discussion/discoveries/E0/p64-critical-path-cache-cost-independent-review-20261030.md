# Independent review: P64 critical path and cache cost

Reviewer: `/root/teal_full_llm_calibration_build_terra`. Reviewed author version SHA-256 `69f049412ae5308e3200b6c0d78f0db57e32c8a975d8d82ecbdcdd7c32138013`. Disposition: **SUPPORT the bounded SRC/ALG interpretation; competing mechanisms remain OPEN.** The final author version corrects source-relative links; the scientific claims were reread and the conclusion remains unchanged. This review is static and authorizes no experimental scope.

The original timed wrapper records start/end events around the saved `infer_ffn`; V2 installs its outer wrapper after the original tap. Consequently its per-expert `empty_cache` executes after the saved timed wrapper has returned, outside the event endpoints; the candidate operations dispatched from within the original call are inside them. Events are compute-stream elapsed intervals, so host delays and synchronizations can affect elapsed time, and their sum is not automatically a serial wall-clock decomposition. The driver wall starts before `pipe.generate` and includes synchronization, tap completion and video inspection, but excludes pipeline creation. The actual offload loop submits next-block prefetch before current compute; `swap_blocks` synchronizes load and compute streams. These observations support the author's stated boundaries, not an inference that transfer is saturated or a particular overlap fraction.

The max(C,L) expression is valid for its explicitly idealized concurrent independent segments and is not a measured decomposition; its stated benefit can range from zero to ΔC. The 1.158 Amdahl figure is conditional on event time being a removable nonoverlapping critical-path component and all else staying fixed, so it is not an unconditional bound. A and B can coexist. An additional counterexample for attribution is a host-side delay within the recorded stream-event interval or an observer-induced synchronization that changes load overlap: a larger event need not equal a larger kernel service demand, and a timing profile can itself change the schedule.

The proposed timeline must separately record actual GPU copy/compute intervals, CPU enqueue and event/synchronization waits, with its observer overhead measured against a matched minimally instrumented run; otherwise join wall and GPU active time can be double counted. A resident/shorter-cache action changes both resource allocation and potentially numerical behavior, so compare it against same-runtime Dense and P64 with matched warmup/order and verify output/quality separately. If memory capacity prevents co-residency or measured overhead cancels gains, that is a negative result for this action, not for every possible offload schedule. The existing two-source, one-seed, fixed-order measurements do not identify the dominant mechanism.
