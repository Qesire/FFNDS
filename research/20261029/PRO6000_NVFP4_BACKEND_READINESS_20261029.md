# PRO6000 NVFP4 backend readiness · 2026-10-29

**SRC / OPEN:** The existing LightX2V implementation has a concrete full-FFN W4A4 route: `MMWeightWnvfp4Anvfp4dynamic.apply` calls `scaled_nvfp4_quant_sm120` on each real input and then `cutlass_scaled_nvfp4_mm_sm120` with packed W and A, their independent scales, alpha and bias. Each W1 input and each post-GELU W2 input must be quantized at its own real call. W and W scales are static checkpoint data; the input global scale is derived from checkpoint `input_absmax` or read from an alternate stored global-scale path, while each call produces its own dynamic 16-element activation block scales. The expected checkpoint keys are source-derived until downloaded headers are checked.

The two checked PRO6000 project environments report Python 3.11.15 (`cpython-311-x86_64-linux-gnu`) and Torch 2.10.0+cu128. Package metadata and module-spec inspection found neither `lightx2v-kernel` nor FlashInfer in the checked environments; `scikit-build-core` and `uv` were also not installed. No GPU-initializing framework package was imported. The scoped search found no existing LightX2V kernel shared object in the local code view or checked project environment; other locations are not ruled out.

A metadata query of the [official PyPI project](https://pypi.org/pypi/lightx2v-kernel/json) returned HTTP 404; the [official repository releases API](https://api.github.com/repos/ModelTC/LightX2V/releases?per_page=100) listed two releases without a kernel wheel asset. Within these checked primary sources, an official precompiled wheel matching the Python ABI, Torch and CUDA has **not been verified**, so there is no verified wheel URL or SHA to bind. The [official build instructions](https://github.com/ModelTC/LightX2V/blob/e1088278f1f34547731cfd7405952e67ed36b695/lightx2v_kernel/README.md) instead build a wheel against Torch and CUTLASS. This limited search is not proof that no suitable wheel exists elsewhere.

The local LightX2V code view has no upstream Git identity. Its exact 51-file kernel closure is listed and individually SHA-bound in the companion JSON, with manifest SHA `7fe7a2352edef0ec0de009ee7fffc5e4bf4f925d99c3b5df6e52b2e0d88cad1b`; the FFN dispatch file is separately bound there. A public upstream candidate commit `e1088278f1f34547731cfd7405952e67ed36b695` supplies a related `lightx2v_kernel`, but four local files differ and three upstream files are absent locally; it is a distinct candidate, not a provenance claim for the local snapshot. The existing CUTLASS repository is independently pinned at `d55f6beeebb6df501a250dc82827db97660f06e0`, matching the historical primitive record.

A minimal **future, separately registered** source-build route is a new node-local overlay with a frozen choice of the exact source closure or the upstream candidate, pinned build dependencies and CUTLASS, Torch 2.10+cu128 and a verified CUDA 12.8 compiler, targeting `sm_120a`. The inspected CMake contains `--threads=32`; a recorded overlay-only patch to `--threads=1`, `MAX_JOBS=2`, `CMAKE_BUILD_PARALLEL_LEVEL=2` and two-CPU affinity are needed to honor that proposed CPU budget. Freeze the patch, tool versions, inputs, output SHA and logs before a build. Do not install into the existing frozen environment. No build or GPU execution is claimed by this readiness check.

The historical CUTLASS 79a executable is still present and matches SHA `76d3f50c28c341da27d4c89faac45391aa25b21100ed0261bd9900f4fc6ba5f0`; it is a standalone packed primitive, not the LightX2V extension. Once an extension and matching checkpoint are bound, the decisive next evidence is registered full-M W1/GELU/W2 W4A4 with actual activation packing and both scale operands, then one full video using the matching official recipe. That recipe requests dynamic sparse attention/Sage; an SDPA fallback can be a separately registered changed recipe, not an official-recipe result. Original BF16, old HiF4 and native NVFP4 checkpoint identities stay distinct.
