# A100 → H20 迁移必读

**本项目原配置专门为 A100 调整；接收方预计使用 H20，但尚未在目标机器确认型号、显存、驱动或执行任何验证。归档不是已经适配/验证的 H20 运行包。** 原服务器路径、A100节点约束、编译参数和性能结果作为历史证据保留，不在原始源码里批量替换。

H20 被 NVIDIA 列在 Hopper 产品类别；不能拿 H100/H200 的性能、显存或完整指令支持替代目标 H20 的实测属性。先用包内 `tools/hardware_probe.py` 获取当前实际分配设备的名称、compute capability、显存和软件版本。型号仍以现场输出为准。[NVIDIA H20 类别](https://docs.nvidia.com/ai-enterprise/release-8/latest/infra-software/vgpu/reference/hopper.html)

## 编译兼容性不能靠换一个字符串保证

A100 是 compute capability 8.0。NVIDIA 的兼容指南区分原生cubin与PTX：仅面向Ampere的二进制不能被当作Hopper原生二进制；包含合适PTX时可能JIT前向兼容，但仍需实际加载与数值检查。[GPU CC表](https://developer.nvidia.com/cuda/gpus)，[Hopper兼容指南](https://docs.nvidia.com/cuda/hopper-compatibility-guide/)

接收方应在**分配到H20的计算节点**运行：

```bash
python tools/hardware_probe.py --output hardware_h20.json
```

检查 `torch.devices[].compute_capability`、`name` 和 `total_memory_bytes`。若实测CC为9.0，使用目标库支持的9.0构建目标；不要在未探测时硬编码。`TORCH_CUDA_ARCH_LIST` 并不控制所有库自己的NVCC/CMake参数，且设置它不会重建已经安装的wheel。`sm_90a`也不应由本包自动推断。

建议在新的虚拟环境和构建目录操作。保持生成与VBench两个环境隔离。归档中的pip版本是原环境观察值，不是H20安装脚本；先核对驱动/torch wheel/CUDA toolkit/编译器/扩展ABI是否配套，避免一次性升级全部依赖后无法定位变化。

## 第一轮验证保持变量尽量少

1. 保存硬件探测JSON、环境版本与新site配置；确认没有继承学校A100节点限制。
2. 先复现dense D-BF16与dense D-Q，保持原四步列表、CFG关闭、torch_sdpa、GELU(tanh)、offload及量化/写回顺序。不要同时切到FlashAttention-3、FP8或新量化后端。
3. 在小范围匹配输入上检查有效W2布局、bias一次、smooth/QDQ、gate和cast。再比较latent轨迹/视频；允许跨后端浮点差异但须记录，不能预设位级相同。
4. dense基线稳定后，再在H20上测试稀疏候选和完整40×4 FFN计时，包含路由、QDQ、packing、修正和搬运。
5. 重跑正式20条seed42三项评测；生成与评测硬件和环境分别记录。同事GPU若不是H20，按实际设备重新解释全部结果。

## 结果如何报告

- A100历史速度与H20新速度分表；不能把A100 dense时间除以H20候选时间。
- H20的加速比用同机同环境 `sum(T_dense)/sum(T_candidate)`。既有1.5×目标仍是待验收目标，不是H20预期收益。
- AR1的47.25%–92.47%来自CPU局部回放，既不是A100速度，也不是H20速度。
- 不因H20有不同硬件能力，就把HiF4 native QDQ+BF16投影称为硬件原生INT4/FP4推理。FP8/其他硬件路径若启用，应作为独立arm重新验证。
- 本次只编写迁移说明与探测工具，没有接触同事H20、安装软件、重新编译或执行H20模型实验。
