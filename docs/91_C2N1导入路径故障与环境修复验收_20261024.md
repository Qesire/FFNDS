# C2N1：真实启动失败与环境修复

C2N1在空闲A10080GB PCIe上完成一次CUDA启动，随后因`ModuleNotFoundError: No module named 'HiFloat4'`退出。视频、独立FFN、额外norm和selector均为0；算法质量与速度未测，也没有人工视频审阅对象。

错误来自本轮Agent的启动命令：在原生模型入口前额外套用了`worker_eval_env.sh`。该脚本清除`PYTHONPATH`，随后的Transformers源码视图只追加自身目录，项目中的HiFloat4/LightX2V因此不可导入。这个环境脚本选择不应进入原生模型链。

已保留[原始数值](../research/20261023/C2N1_native_results.json)、[固定预算](../research/20261023/C2N1_budget.json)、[真实退出/资源凭证](../research/20261023/C2N1_completed_resources.json)、[故障解释](../research/20261023/C2N1_startup_failure_analysis.json)和[实际执行源码清单](../research/20261023/C2N1_executed_source_manifest.json)。53份实际源码、490,667字节保存在原HF结果目录；后续修复不覆盖它们。原授权写明单次尝试、失败不自动重跑，C2N1已经关闭，资格为空。

本次同进程早期占用取得NVML可见上下文：逻辑张量1字节，实际自身占用416MiB，取得占用0.801105秒，有限启动采样无外部计算。它尚未覆盖长时间资产加载或视频生成的隔离行为。用户新授权的七个节点已检查，选取与原对照相同类型的A100；约128GB既有运行时资产已进入HF缓存，[12份模型载荷完整SHA256及硬链接核验](../research/20261023/C2N1_mirror_preflight.json)通过。节点名仅保留在私有配置中。

[新模型环境入口](../scripts/worker_c2_model_env.sh)恢复项目配置中的导入路径，保持既定CUDA UUID或明确为空的CPU可见性，并清除CPU检查专用的平台跳过标志。[执行前检查](../tools/c2_environment_contract.py)在导入Torch、建立CUDA上下文之前核对两个包的真实来源，避免同类错误再次消耗GPU启动。

CPU上已完成正反核验：

- 原错误链可重复得到HiFloat4/LightX2V缺失，Transformers存在。
- 修复链能够导入HiFloat4适配器、LightX2V及原生推理类；D-Q组合缓存完整SHA256匹配，160处原参数全部读取校验通过。
- 所有GPU明确隐藏，`torch.cuda.is_initialized()`为False，没有FFN、norm、selector或生成调用。
- LightX2V源码在导入时检查设备，因此CPU检查内部明确启用了其提供的`SKIP_PLATFORM_CHECK`。该事实保存在[正向CPU结果](../research/20261023/C2N2_environment_CPU_preflight.json)；实际模型启动器会清除这个标志，仍执行真实设备检查。这次CPU结果不验证原生数值或视频。

[新固定草案C2N2](../research/20261023/C2N2_environment_smoke_DRAFT.json)仅修复启动环境，六臂生成循环AST与C2N1相同，评分、动作、补偿、source6、seed42与全部160位置均不变。单张空闲GPU；6条完整视频、2norm、3selector，零独立FFN/训练/分解/官方评分，新增结果≤0.5GiB，失败不自动重试。使用独立HF输出与预算，不重开C2N1。执行仍需新的独立授权。

复核：`python tools/check_c2_environment_preparation.py --check`、`python tools/check_c2_reserved_results.py`，以及`test_c2_model_environment.py`、`test_c2_environment_contract.py`。旧[72位置目标边界审计](90_原生残差写回与下一归一化的目标错位审计_20261024.md)也已保存，新增模型调用为0；本轮继续以实际完整视频作为冻结算法的下一里程碑。
